01

Why Agent Quality Beats Cost

The mindset shift that makes every other tip work: stop gambling, send fewer and better agents.

Act 1. This is the philosophical core borrowed from the Reactor talk. If they only get one act, this is it — the rest are tactics that serve this idea.
why this matters

The bill moved onto your desk

  • GitHub shifted from premium requests to usage-based billing — which surfaced a flood of "how do we cut token spend?" questions.
  • GitHub used to absorb the cost: it made money on small requests and lost money on huge-token ones. Compute isn't cheap anymore.
  • But optimizing for cost alone diminishes the value you get from Copilot. The better question: how do we make the most of the tokens we spend?
Reframe: don't count tokens — make every token count.
Motivation. The billing change is the "why now." But pivot immediately away from pure cost-cutting — that's the trap. Quality is the lever that also happens to cut cost.
the anti-pattern

We've all been gambling

🚀 the NASA analogy

"If rockets were cheap, NASA could fire 20 roughly at the moon. If one lands, great. If none do, fire the next 20."

That maps exactly to how agents get used: little context, a lazy prompt, send it — and if it fails, just send another.

Why it no longer works

  • Fine at 2–4 agents/day
  • Unsustainable at dozens–hundreds/day per dev
  • Sessions get longer → more tokens → more cost
  • And now you pay for the misses
The wrong fix: "How do we make the fuel cheaper?" — that's just asking how to keep gambling.
The memorable analogy. Lean into the rocket image — it sticks. The punchline: making fuel cheaper = keep gambling. The right move (next slide) is sending fewer, better rockets.
the shift

Fewer rockets, aimed better

  • Increase the value of each agent before you send it — give it enough context to actually hit the target.
  • Fewer agents automatically means fewer tokens. Quality and cost move together.
  • Think ROI per agent, not cost per token. You can't always quantify the value cleanly, but the direction is right: optimizing cost when value is zero is useless work.
Bonus: raising value usually means using fewer tokens — because most waste is irrelevant context the model re-reads (and you re-pay for) every single turn.
The pivot. SpaceX/NASA don't launch rockets they know will explode — they're precise. Same with agents: invest in the prompt/context up front so it lands. Fewer + better = cheaper, as a side effect.
the math that justifies everything

The compounding-error problem

99%accuracy per step…

…over 50 steps = 61% overall

95%accuracy per step…

…over 50 steps = 8% overall

↑every quality gain

compounds your odds of success across the whole run

LLMs are non-deterministic — they have an error margin and multi-step agent work compounds it. Each miss wastes tokens and spawns bug fixes, reviews, reruns, and incidents.
This is the killer slide. The 95%→8% number shocks people. It's why a small per-step quality improvement matters enormously, and it sets up the whole "deterministic guardrails / tests" section in Act 4. Non-determinism is the enemy; quality controls are the answer.
how much should you care?

The maturity spectrum

assistant user

~10 agents/day

Synchronous, AI-as-assistant. Spend ~$20/mo? Saving 50% gets you to $10 — not worth heavy tuning. Use the basics and move on.

AI engineer

100s of async agents

Orchestrating dozens–hundreds of agents. Every 1% of tokens and 1% of quality compounds across the fleet — tuning pays for itself.

The tips ahead are ordered by leverage. Lower-maturity teams: focus on the first few. High-throughput teams: all of them.
Calibrate effort. Be honest that not everyone needs every optimization. This earns credibility — you're not selling busywork. Ask the room where they sit.
02

Foundations

How LLMs, agents, and context windows actually work — enough to judge any token tip you read online.

Act 2. Short but essential. The goal: give them the mental model to evaluate the hundreds of (often wrong) token tips circulating online.
what an llm is

A stateless, text-in/text-out machine

Word-probability engine

Given input + training, it predicts the most probable next word (or next instruction, for code). Models got better; the principle didn't change.

It has no memory

An LLM doesn't store your conversation. "Having a conversation" means re-sending the entire history — every input and output, in order — on every turn.

Consequence: tokens and context compound as a conversation grows. Statelessness is the root cause of token cost.
Foundational. Statelessness → re-send every turn → compounding cost. This single fact explains why long threads are expensive and why /clear matters. Everything downstream traces back here.
the core principle

The Goldilocks rule of context

too much

Bias & noise

Irrelevant info biases the model toward wrong answers. It can't distinguish relevant from irrelevant — it weighs everything.

too little

Hallucination

It misses critical info and fills gaps by hallucinating. There's no error for missing context — "the math makes no distinction between fact and hallucination."

"As little context as possible, but as much as required." Finding that band is the skill: context engineering.
The thesis restated technically. Both failure modes are real — over-stuffing isn't "safe." Name the skill: context engineering. This is the term they'll hear all of Act 4.
the moving parts

Agents are just apps. The LLM is just the model.

Harnesses (the agent)

  • VS Code Chat — where it started
  • Copilot CLI
  • Copilot Cloud Agent (github.com)
  • 3rd-party: Claude Code, OpenAI Codex

Models (the LLM)

  • GPT · Claude · Gemini · Microsoft models
  • The agent talks to the model dozens of times per request, on your behalf
  • Each call carries a token cost
Your levers to steer it: the prompt · the files in your project · the agent config (instructions, skills, MCPs). The harness shapes quality — but you still drive.
Vocabulary slide. Separate harness from model — people conflate them. The "agent talks to the LLM dozens of times per turn" point previews why agent runs burn tokens. End on the levers, which Act 4 details.
under the hood

The context window, re-sent every loop

# Loop 1
system prompt + tool descriptions + your prompt + file refs   → INPUT tokens
model response                                          → OUTPUT tokens (pricier)

# Loop 2+
everything from loop 1 + previous responses + new input   → MORE tokens
≈¾word per token
50–200Ksmaller-model window
1Mlarge models ≈ LOTR + Hobbit
Make compounding concrete. Walk the loops: each turn re-sends all prior turns. Don't go deep on tokenization — keep it at "prompts, files, responses cost tokens and compound." The 1M ≈ LOTR fact is a nice scale anchor.
two failure modes to design around

Lost in the middle · Recency bias

🎯 Lost in the middle

The model favors the start (instructions/goals) and end (current work), neglecting the middle. Switch tasks mid-session and it can snap back to the original task.

→ New context window per distinct task.

⏱️ Recency bias

Above ~50% capacity it starts favoring only recent content — forgetting your system/original prompt and drifting.

→ Keep the window under ~60–70% unless necessary.

Not absolutes ("we're not Sith") — you'll sometimes run to 80–100%, and that's fine. These are biases to manage, not laws.
Technical depth payoff. These two biases justify "new session per task" and "keep it under 70%" — which are Act 4 habits. The Sith joke is from the talk; use it to soften the rule into guidance.

The Billing Model

What actually gets counted, what it costs, and the two highest-leverage levers — model choice and relevant context.

Act 3. Now the concrete billing mechanics. Two systems coexist right now (legacy multipliers vs new credits) — flag which plan the room is on.
the 2026 shift · live now

Premium requests → usage-based AI Credits

legacy

Premium Request Units

1 prompt × model multiplier, against a monthly allowance. Still active for legacy annual Pro/Pro+ until the plan expires.

current · June 1 2026

GitHub AI Credits

1 credit = $0.01. Cost = model × tokens consumed (input + output + cached) at each model's API rate.

Two systems are live at once. Ask the room which plan they're on. Note: code completions / Next Edit suggestions stay unlimited and unmetered.
github.blog usage-based-billing · docs.github.com models-and-pricing ✓ verified 3-0
Honesty: this changed days ago and GitHub says it's "subject to change." Durable points: credits = tokens × rate; completions free; legacy plans still on multipliers.
what gets counted

Your prompts count. Tool calls don't.

✓ Counts as a request

  • Each user prompt in Chat / agent mode
  • /plan in CLI = one; each follow-up = another
  • Cloud coding agent = one request per session × rate

✗ Doesn't add a request

  • The agent's autonomous tool calls
  • File reads/edits/terminal runs it does itself
  • Multi-step reasoning within a turn
Implication: one well-scoped prompt that lets the agent run is cheaper than ten babysitting follow-ups. (Tokens still accrue under credit billing — but the "fewer, better prompts" lesson holds.)
docs.github.com about-premium-requests ✓ 3-0
Counterintuitive. Agent mode's 40 tool calls are free (request-wise); only prompts count. Reframes "agents are expensive" → "write better single prompts." Ties to Act 1's "front-load the prompt."

lever #1 · how to choose

Reasoning models aren't always better

reasoning models

Plan & think

  • Planning & architecture
  • Debugging complex bugs
  • Synchronous work you're driving
  • Large-context, many-file tasks
smaller models

Execute

  • Implementation after planning
  • The reasoning already happened in the plan
  • Documentation, simple edits
Watch out: a reasoning model handed a tight spec may reopen the plan, second-guess it, and go rogue. For execution, a lighter model often gives better quality, not just cheaper.
Nuance most people miss. Bigger ≠ better for implementation. The "goes rogue on a tight spec" point is memorable and true. This sets up the plan→implement split in Act 4.
lever #1 · free wins

Auto selection & the 0× fallback

Auto model selection

Now task-aware (not just availability) — it reads your context and picks a fit. Plus a 10% token discount. Well received in the field.

# a 1× model via auto:
1.0× → 0.9×

Base-model fallback

Spend your premium allowance and you can keep working all month on the 0× included model — and it's the right default for low-stakes work anyway.

May be rate-limited at peak demand.

github.blog auto-model-selection · docs.github.com about-premium-requests ✓ 3-0
Two easy wins. Auto = free 10% + behavioral nudge toward cheaper models. Q&A note from the talk: auto excludes the priciest models (Opus 4.7) and leans mid-range. Fallback reframes "out of requests" as "switch to free," not "stop."
04

Context Engineering

The heart of the talk. Every tip here is a context-engineering technique — discipline, workflow, guardrails, and config.

Act 4 — the longest. Lever #2 = provide only relevant context, expanded into five subsections. If short on time, the structure doc flags 4D/4E as trimmable.
discipline · do this daily

New task → new session

anti-pattern

One mega-thread

Reusing a conversation for unrelated tasks drags all prior context — and its cost — into every new question, and triggers recency drift.

do this

/clear liberally

Start fresh per task. Tokens don't carry across sessions, so throw away context without hesitation. Don't steer a session bloated past ~80%.

Speaker's preference: reach for /clear and restart over /compact — compacting can lose relevant info and cause misses (more on that shortly).
Simplest, highest-payoff habit. Reflex: finish task → /clear. Connect to Act 2's recency bias. Foreshadow the compaction caveat.
discipline · scope the inputs

Provide only relevant context

efficient
#file:src/auth/login.ts
#BasketAddItem   # a single method

Name the files/symbols you know are involved. Let the agent discover the rest itself.

expensive by default
@workspace  #codebase

Searches the whole repo and injects snippets at high token cost. Don't attach the entire project for a small change.

Don't pre-stuff "I might need this." Give exactly what's needed and nothing more — reserve whole-codebase context for genuine discovery/navigation.
code.visualstudio.com context docs · learn.microsoft.com context-references ✓ 3-0
Copyable syntax. #file/#symbol efficient; @workspace expensive. The "let the agent discover" point matters — over-providing is as bad as under-providing (Goldilocks).
discipline · steer from the start

Precise prompts beat short prompts

✗ "Fix the bug."

The agent may hunt, find the wrong bug, and do unrelated work — then you re-do it.

✓ "Issue #45 describes a bug where XY happens. Fix it."

A couple more tokens; far fewer misses.

  • Don't shrink prompts for tokens — the prompt is always-on context with outsized influence. Optimize it to steer correctly.
  • Tell it to stop when tests pass — prevents unnecessary commits/pushes/extra work.
  • Provide known context up front: file locations, docs to fetch, skills to invoke.
Precision ≠ brevity. The "Fix the bug" vs "Issue #45" contrast is the talk's best concrete example. "Tell it to stop" is an easy, overlooked token saver.
discipline · the caveat

Compact carefully

What it does

/compact summarizes earlier turns to reclaim window space. Auto-triggers around ~80% in the CLI.

The risk

It loses information. If that info was relevant → agent misses, and your token savings become a quality loss. The speaker has seen it cause hallucinations.

Rule of thumb: prefer /clear + a fresh, well-scoped restart over compacting a bloated session. Use /compact only when the thread is genuinely still valuable.
Honest nuance. My earlier deck recommended /compact freely; the talk pushes back — the speaker rarely compacts manually. Present both: compaction is a tool, but /clear is often safer. Token savings that cause misses aren't savings.
workflow · do this daily

Research → Plan → Implement

1 · research

Load context, explore (/research). Pulls in lots of files — not needed for implementation.

2 · plan

Use a reasoning model in plan mode to produce a precise spec / to-do list that leaves no room for variance.

3 · implement

Execute the spec with a lighter model — the thinking already happened.

Use a NEW context window per phase. Doing all three in one session carries research junk through every turn — degrading quality and wasting tokens (even cached). Some duplication is worth it.
The flagship workflow. Phase isolation is the big idea — research context is poison for implementation. New window per phase. This is where model-choice (Act 3) and context discipline combine.
workflow · scale out

A clear spec unlocks parallel agents

  • With a precise spec, split work by architectural layer and run multiple agents in parallel.
  • Define contracts between components so each agent works independently.
  • Each agent carries only its relevant context — no shared bloat, less drift, more throughput.
This is the "AI engineer" mode from Act 1's maturity spectrum — and it only works because the planning phase produced a spec tight enough to parallelize against.
Payoff of good planning. Parallelism requires contracts + scoped context. Tie back to maturity spectrum: this is what high-throughput looks like. Saves wall-clock and tokens simultaneously.
guardrails · the antidote to compounding error

Tests are context engineering

500PRs/week shipped by the Copilot CLI team
50%of their codebase is tests
99%a failing test snaps a drifting agent back to ~99% accuracy
A test is a deterministic control — it fails or it doesn't, no wiggle room. It directly counters the compounding-error problem from Act 1: the agent can't build a buggy change on a buggy change because the gate stops it.
Microsoft Reactor talk — Copilot CLI team practice
Callback to the 95%→8% slide. Tests are the fix for non-determinism. The 50%-tests stat lands hard. Deterministic gates reset accuracy mid-run. This is the most underrated token-saver — bugs are the expensive thing.
guardrails · beyond tests

Whatever you can make deterministic, do

Stack the gates

  • Tests (the big one)
  • Linters
  • Security scanners
  • Any code-architected guardrail

No guardrails = incidents

Without tests the agent stacks buggy change on buggy change. It finishes faster/cheaper — but you get a bug or incident: wasted CI minutes, review cycles, reruns, human debugging that fills the next context window.

Shift left. 15 years of "test early" is even more true for agents than for humans — the accumulated cost of a miss dwarfs the cost of the test.
Cost reframe. The cheapest-looking run (no tests) is the most expensive once you count the incident. Shift-left is the through-line. Guardrails are context engineering because they constrain the non-deterministic model.

config · the always-on tax

Keep instruction files tiny

What belongs

  • Non-negotiables — project guardrails every agent must follow
  • Miss-prevention — wrong build/test command, recurring errors
  • Output trimming — "be concise, only return code"

Myth-bust

Instruction files don't reduce tokens — always-on files are injected into every request and add tokens. (This claim was specifically refuted in research.)

  • Don't AI-generate them — they get "speaky" and imprecise. Write from observed behavior and iterate.
  • Recreate often — the CLI team throws theirs out every ~3 months as it goes stale.
code.visualstudio.com custom-instructions · docs.github.com repository-custom-instructions ✓ 3-0 (myth refuted 1-2)
Two truths: (1) these are a per-request tax — keep them lean; (2) the "instructions save tokens" myth is false. Value = quality/consistency, not savings. The "recreate every 3 months" practice surprises people — these are living docs.
config · output is the priciest

Trim the output, not the politeness budget

  • Output tokens are the most expensive. Instruct the agent to be concise, drop niceties, and return only code where appropriate.
  • Research shows "be concise" yields nearly the same quality as elaborate prompting — you're not trading accuracy for brevity here.
  • The famous aside: OpenAI reportedly "lost millions" on people typing please and thank you. Same idea applies to what you ask the model to return.
This is the one place to optimize for fewer tokens directly — output, via a standing instruction — because it doesn't cost you quality.
Nuance: earlier I said "don't shrink prompts for tokens" — that's INPUT. OUTPUT is different: trimming it is a real, safe saving. The politeness anecdote is a crowd-pleaser; use it to make the output-token point memorable.
config · roles & dynamic loading

Custom agents & skills

Custom agents

Force a role/workflow, invoked manually (e.g. a TDD-red agent that only writes failing tests). Write the prompt once, reuse it.

Restrict its tools to prevent wrong paths — e.g. read-only on a GitHub issue so it can't edit it.

Skills

Like custom agents but loaded dynamically — the harness offers the skill, and the LLM pulls it in only when the task matches ("lazy context"). Keeps it out of always-on context.

Best practice for skills: don't overdo it; skip redundant ones (the model already knows React); only add capabilities the agent lacks; toss them as models evolve.
Key distinction: custom agents = manual + tool-restriction (prevents wrong paths, the real benefit); skills = dynamic/lazy (saves always-on context). Tool restriction is a small token lever but a big quality/safety lever.
config · external tools & isolation

MCPs & sub-agents — use with care

MCPs

Add external tools but dump tool descriptions into context (token bloat) and can trigger undesired tool calls.

Playwright MCP: great for front-end, but screenshots/page-reads are token-heavy. Don't leave always-on — scope it into a custom agent.

Sub-agents

Open a second context window for a task (e.g. research), process docs there, and return only a summary to the main session.

Keeps the main session clean — at the cost of tokens spent in the sub-agent. Conditional optimization.

Also: Copilot memory auto-learns in the background; scoped instructions help monoliths; prompt files are fading in favor of skills/custom agents.
MCPs are a double-edged sword — deactivate unused ones. Sub-agents are powerful but not free (they spend tokens to save context). "Conditional optimization" = use when needed, not always.
config · power-user tips

For the high-throughput crowd

Think in code

Scripts to filter outputs before analysis — e.g. trim the GitHub REST API to relevant fields only.

CLIs > MCPs

Tools like gh are already known to models and leaner than MCP equivalents.

Shell output trimming

Tools like RTK cut CLI output down to agent-relevant info.

/chronicle

Analyzes your CLI session logs and suggests prompt optimizations.

Collapse tool calls

Batch multiple calls into one to cut turns.

Model-specific tuning

Only for 1000s-of-agents power users — models change too fast to be worth it otherwise.

Advanced, trade-quality-for-tokens territory. Flag these as power-user only. Chronicle is genuinely useful for anyone wanting data-driven prompt improvement. "Think in code" is the mindset: deterministic filtering beats asking the LLM to filter.
